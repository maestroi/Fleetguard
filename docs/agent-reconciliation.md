# Opt-in agent policy reconciliation (issue #9)

**Lab-only.** The existing `fleetguard-agent -config examples/agent.json` still runs a no-network, no-firewall, one-shot simulator. The new `-run -runtime-config` daemon is a separate explicit path. Default runtime mode `observe` only uses the in-memory mock backend. No real rules are written.

## Signed policy polling and storage

The daemon polls the existing HTTPS controller `GET /v1/snapshot?group=...` with `Authorization: Bearer <node token>` and `X-Fleetguard-Node-ID`. TLS certificates are validated against a locally installed CA file, with TLS 1.3+, no redirects or HTTP proxy, and only explicit private/loopback/Tailscale IP controller endpoints. Each reply is strictly decoded and verified against locally pinned Ed25519 signing keys, the exact node/group audience, expiry, local protected CIDRs and port/service scopes.

- Signatures are verified over the original canonical payload, not reconstructed fields.
- The accepted signed envelope, monotonically increasing revision and original local acceptance time are saved atomically to a private state directory. **Persistence precedes application**; disk failure blocks a policy update.
- The same exact signed envelope may be polled repeatedly without increasing the revision or extending offline validity. Same-revision mutations and older revisions are rejected.
- At startup the stored envelope is cryptographically reverified at its original acceptance time, then only unexpired/locally authorized decisions are considered. A corrupt or wrongly owned state file fails startup; it is never silently reset.
- Every second by default, the local reconciler prunes expired decisions and compares desired state against the selected backend. A firewalld reload is repaired by replaying only the still-valid desired set and scoped rules.
- A missing controller cannot create new fleet decisions. A policy is usable for at most the **lesser** of its signed snapshot expiry and the locally configured max offline age (1-300 seconds); individual decisions may expire sooner.
- Locally justified temporary decisions have an API but are not linked to any real sensor yet. Only verified application evidence, or TCP established-connection evidence, is eligible. They must pass all local safety checks, and are not persisted after a crash. Unverified network/UDP logs cannot promote automatic bans.
- The controller receives authenticated `validated` acknowledgements in observe mode and `applied` only following a successful real-backend reconcile/readback. Signed but locally unsafe proposals send `rejected`; backend errors send `error`. Unauthenticated/corrupt envelopes are not assigned a trusted revision and therefore cannot be acknowledged as legitimate.
- Ack backlog has one bounded slot; polling retries with capped exponential backoff and jitter. The clock-driven reconciliation loop is independent of the controller.

## Rootless observe-mode lab setup

First run the existing [controller lab](controller-api.md) on loopback or a private test VLAN; use a unique bearer token and the `signing.pub` generated by `fleetguardctl generate-signing-key`. The signing public key is a single base64-encoded Ed25519 public key, not the private key.

Create a `trusted-keys.json` using the controller's actual `signing_key_id` as the key and the *contents* of its `signing.pub` as value, for example:

```json
{"lab-policy-key-1":"REPLACE_WITH_BASE64_PUBLIC_KEY"}
```

Use `examples/agent-runtime.observe.json` as the runtime config template. Replace all `/replace/...` paths with absolute, local paths, install the controller CA certificate and per-node token into private files, and set the `node_id` and `service_group` to the authenticated controller registry membership. The safety file must protect all management and controller paths and authorize exactly the intended service scopes. For offline loopback tests, choose management interfaces present on that VM.

```sh
mkdir -m 700 -p "$HOME/fleetguard-lab/agent-state"
chmod 600 "$HOME/fleetguard-lab/token" "$HOME/fleetguard-lab/trusted-keys.json"
fleetguard-agent -run -runtime-config "$HOME/fleetguard-lab/agent-runtime.json"
```

The agent writes JSON status lines (revision, last successful poll, applied/simulated decision counts and any last error). No node listener or inbound port is opened. Ordinary `fleetguardctl check-config` only validates the legacy one-shot bootstrap; the new runtime config is independently validated by the daemon.

## Disposable VM-only firewalld experiment

**Do not use this on a production validator or Proxmox host.** Only set `mode: enforce` on an isolated test VM with Proxmox console access, a snapshot and recorded recovery procedure. Copy `examples/agent-runtime.lab-enforce.json` and adjust the real IPs, explicit zone, local port bindings and signing key IDs. All of these must be true before the daemon will create any drop:

1. The runtime config, token, trusted keys and safety policy are **root-owned 0600** in symlink-free root-owned directories. The state directory is persistent `/var/lib/fleetguard`, root-owned 0700, including safe parent directories.
2. Local safety policy `mode` is `enforce`, management interfaces and controller IPs are protected, and `host_input_verified` is set only after VM INPUT priority/management-path packet tests. The exact `lab_confirm` value is `disposable-vm-console-ready`.
3. The INPUT interface is bound to the zone **permanently** (`firewall-cmd --permanent --zone=<zone> --add-interface=<nic>`). If the binding is runtime-only, `firewall-cmd --reload` removes it and the backend fails closed until the binding is restored.
4. Operator pre-provisions the Fleetguard-owned `hash:ip` sets; the adapter manages only their runtime entries and matching scoped rich rules. See [firewalld backend guide](firewalld-backend.md). FORWARD/Docker traffic is unsupported.
5. Use short decision TTLs. The controller publishes a lab decision only after [explicit operator approval](correlation.md#approve-a-scoped-decision-in-the-isolated-lab).

Launch only after isolated-VM gates are satisfied:

```sh
sudo fleetguard-agent -run -runtime-config /etc/fleetguard/agent-runtime.json
```

For **immediate**, offline cleanup from a console:

```sh
sudo fleetguardctl emergency-disable -state-dir /var/lib/fleetguard \\
  -runtime-config /etc/fleetguard/agent-runtime.json
```

The CLI creates a root-owned latch **before** attempting backend connection/removal. It clears only the fingerprinted owned runtime IP sets and exact generated rich rules; any D-Bus failure is reported as a partial cleanup failure. A running agent independently sees the latch on the next reconcile and attempts cleanup too. Restarting the agent never removes this emergency latch; only an authorized local operator may deliberately clear it.

**Crash and hang handling (#47):** the pre-provisioned runtime IP sets do not use kernel timeouts (see [watchdog.md](watchdog.md) for why firewalld `timeout` ipsets are unsuitable). Run the agent with [`deploy/systemd/fleetguard-agent.service`](../deploy/systemd/fleetguard-agent.service). Every backend call is bounded by a 15 s reconcile deadline. systemd `WatchdogSec` is pinged only after a successful reconcile, so a hung or persistently failing agent is killed. `ExecStopPost` then runs `fleetguardctl cleanup-owned` to remove owned drops independently of the agent process. Crash loops latch emergency disable through `OnFailure`. A stored snapshot that no longer verifies, for example after signer rotation, is not restored. The agent still starts and keeps its revision watermark. The safety latch must live in persistent `/var/lib/fleetguard`, **not** a tmpfs-only `/run` path.

## Test coverage and remaining validation

Run `go test -race ./internal/agent/... ./internal/safety/... ./internal/firewall/...`. The suite includes signature changes, replay, protected sources, disk-full acceptance, restart after partial decision expiry, offline TTL, emergency-disable errors, spoofable evidence rejection, firewalld reload using a fake backend, authenticated TLS polling, and bounded pending acks.

**Still required before production:** a disposable-VM packet-path test with known actual source IPs and Tailscale/SSH verified before and after, agent SIGKILL recovery/watchdog verification, verification of controller-issued decisions, and external health/alerting. A mocked readback cannot prove kernel packet order.

See [homelab plan](homelab-poc.md) and [issue #9](https://github.com/maestroi/Fleetguard/issues/9).
